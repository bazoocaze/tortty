| B72 | **`OSC 99` notifications** (kitty) — the identified notification: `title` and `body` as separate pieces, base64 or escape-code-safe text, chunked under one id, updatable and closable by that id, with a click reported back to the child | the other four notification doors are in — `OSC 9`, `OSC 777`, `OSC 9;4` and `OSC 7501`, all in [`VT.md`](VT.md) and all converging on one pipeline — and this one is absent in the worst way: an `OSC 99` falls into the `_ => {}` of `osc_dispatch` (`crates/core/src/term.rs`) and nothing happens, and the `p=?` support query gets no answer — the OSC family has no negative reply at all, silence is the norm there, and the explicit `0 - not recognized` lives only in `CSI Ps $ p` (`DECRQM`) — so a program that checks can only time out and then either fall back to `OSC 9`/`777` or show nothing. **The shape it needs landed on 2026-11-24**: the notification entry already stores `title` and `body` apart with `text` derived, the list already replaces by `(source, id)` and moves the entry to the end, and `notif::Source` already has the unused `Osc99` variant — so what is missing is the wire, not the model. | B73 | **`DECRQSS` and `XTGETTCAP`** — the two DCS queries that can say *no*: `DCS $ q Pt ST` asks for a status string (`m` = the current SGR, `r` = `DECSTBM`, `SP q` = `DECSCUSR`, `" p` = `DECSCL`, …) and `DCS + q <hex names> ST` asks for termcap/terminfo capabilities | the core answers `DECRQM` with the standard `0 - not recognized` (`mode_state` returns `0` at `crates/core/src/term.rs:1742-1762`, reply at `1875`), so its silence on these two is a hole and not a policy: `dcs_done` takes the whole DCS and drops whatever is not sixel (`term.rs:2705`, and the comment there names `DECRQSS` by hand). Both have a real negative — `DCS 1 $ r Pt ST` / `DCS 0 $ r ST`, and `DCS 1 + r Pt=Value ST` / `DCS 0 + r ST` — which is exactly the machinery the OSC family never got (`B72`). The state the answers need is already in `Term`: SGR is `fg`/`bg`/`ul_color`/`flags`/`ul` (`term.rs:230-238`), the scroll region is `top`/`bottom` (`237`), the cursor style is `app_cursor_style` (`249`) | when a program the owner runs asks — anything that probes terminfo at runtime instead of trusting `$TERM` goes through `XTGETTCAP`, and a program that saves and restores SGR around a shell-out asks `DCS $ q m`; both get silence today, and a client that assumes an answer either hangs until its timeout or keeps the state it invented | low-medium: a `dcs_done` branch that recognises `$q`/`+q` before the sixel path, the answers for the settings tortty really keeps (`m`, `r`, `SP q`), the standard `DCS 0 $ r` for every other request, and for `XTGETTCAP` the hex decode plus a small table (`Co`, `TN`, `RGB`, the keys the keymap can send) — the negative has to land for every unknown name, which is the same two bytes the standard already defines |
