# Externals — bugs of other software

A trap or a protocol violation that is **not ours**, kept so the investigation is
not paid twice. An entry enters **when the owner asks**: a measured case with the
proof attached, never a suspicion. It is not a queue ([`BACKLOG.md`](BACKLOG.md)):
nothing here is work for us. When the other side fixes it, the row leaves and the
removal is a line in [`HISTORY.md`](HISTORY.md).

| 2026-11-07 | `pi` 1.4.0 | leaves and the tab stays on its title, no longer following the `cd` | one `process.stdout.write("\x1B]0;${title}\x07")` in the whole `dist` (`dist/bundle/chunks/chunk-T726RZZU.js:107`), **zero** `CSI 22;2t`/`23;2t`, and `restoreOnExit` restores paste/kitty-keyboard/cursor but not the title; in tortty, without pi: socket `write` of `printf '\033]0;x\007'`, then `cd /tmp` → frozen, then `printf '\033c'` → the cwd is back | `reset`, or `OSC 0` in the `precmd` (`B39`) | pi > 1.4.0: open, quit, `cd /tmp` |
| 2026-11-09 | `pi` 1.4.0 | the farewell `To resume this session: pi --session <id>` is **not printed** when the terminal closes — only on an interactive quit | in `dist/modes/interactive/interactive-mode.js`, `shutdown({fromSignal})` takes its own branch (3451-3463) that disposes the runtime and calls `process.exit(0)` **before** reaching `const resumeCommand = formatResumeCommand(…)` (3474-3477), which is what writes the line; SIGHUP and SIGTERM are registered with `{fromSignal: true}` (3551), so a window close can never reach it. Measured: a bare pty (`pty.fork`) running `pi`, `SIGHUP` after 6 s → 16 327 bytes of output, zero `resume` lines; and a recorded snapshot of a tab where a `pi` was running (`~/.local/state/tortty/session-*.ans`, 130 628 bytes with the pi screen) has the frame but not the line | quit `pi` first (Ctrl+D, Ctrl+C twice or `/quit`), then close the window: the line lands on the screen and travels in the `restore_state content` snapshot | pi > 1.4.0: open `pi` in a tab, close the window, `grep -c 'To resume this session: pi --session' ~/.local/state/tortty/session-*.ans` |
| 2026-11-11 | `pi` 1.4.0 | images come out as text and links as `text (url)` — no image protocol is ever picked | `pi-tui` chooses the protocol **only** by terminal name from the environment (`TERM_PROGRAM`, `KITTY_WINDOW_ID`, `GHOSTTY_RESOURCES_DIR`, `WEZTERM_PANE`, `ITERM_SESSION_ID`…, `dist/terminal-image.js:detectCapabilitiesFromEnvironment`); under tortty (`TERM=xterm-256color COLORTERM=truecolor TERM_PROGRAM=tortty`) `detectCapabilities()` answers `{"images":null,"trueColor":true,"hyperlinks":false}`. Our half works: the raw `f=100` sequence draws (22946 pure-red pixels on a captured screen) and the `a=q` probe is answered — and reading `brazil_flag.png` in `pi` with the workaround below drew the picture | `PI_IMAGE_PROTOCOL=kitty` (`PI_HYPERLINKS=1` for the links) | pi > 1.4.0: read an image with the stock environment |
| 2026-11-14 | `chafa` 1.14.0 | after `chafa -f kitty img.png` the shell shows `^[_Gi=1;OK^[\` — the terminal's acknowledgement of the transmission, echoed by the shell as if the user had typed it | the payload of a kitty transmission ends with `m=0` and **no `q=`**, which the protocol defines as "answer me", but the process never reads its own input: `script -qc "strace -f -e trace=read,write -o /tmp/c.out chafa -f kitty --size=8x4 brazil_flag.png > /dev/null"` records **0** `read(0)` calls in the whole run, so the reply — correct, and needed by `kitten icat` — lands in the tty queue after `chafa` is gone and the line editor prints it | none on our side; a producer that does not want to be answered sends `q=2` (`kitten icat` does) | chafa > 1.14.0: `chafa -f kitty img.png` and see whether anything is printed at the prompt |
